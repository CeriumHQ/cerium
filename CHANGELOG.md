# Changelog

All notable changes to Cerium are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow
[Semantic Versioning](https://semver.org/).

## [Unreleased]

### Removed

- The repository's `social-preview.png`: GitHub now reuses the website's `og.jpg`, the same share image `apps/site/index.html` points to, uploaded through Settings → Social preview.

- Harness versions are no longer judged: the "tested with Cerium" label, the "too old for Cerium" block that refused older harnesses, and each adapter's tested range are gone. Whatever version is installed, Cerium drives it. The backend still tells viewers before `RPC_VERSION` 20 every version is "supported".
- Internal: helpers that nothing outside their module reads are no longer exported, and the ones nothing uses (tab, branch, GitHub and file-tree helpers) are gone with their tests.

### Added

- A welcome on a computer's first run. Once the launch screen gives way on a desktop that has no threads yet, its mark flies to the welcome's: Cerium's mark as solid glass in three dimensions, ray-marched in WebGL2, bending and splitting the studio light it sits in and tinted with the theme's accent. It turns in from the side as it arrives, sways slowly, leans after the pointer, and its facet spins in the C's mouth. Next, Choose your glass picks the palette and light, dark or system from a row of panes, each drawn in its own palette and turning towards the pointer; a pick spreads over the welcome as a widening circle from the pane. Only while no harness on the computer can run a thread, a last step lists them as Settings → Harnesses does, with Install, Sign in and Set up running the same flows and Check again to look once more. Enter and the arrows move through it, Escape skips it, the hairlines at its foot go back to a step seen, and focus moves to each step's headline; while it shows, the window under it takes no keys and What's new waits for it, and closing it puts the cursor back in the message box. Finishing or skipping flies the mark back to the window's corner. It doesn't open again by itself (`cerium:welcomed`), nor on a computer that already has threads or on the web client; the command palette's Welcome tour and Settings → General open it again. A GPU that can't keep up draws the glass at fewer pixels; without WebGL2, or in forced colours, the flat mark stands in, and without motion the glass is drawn still and every part fades in. Settings → Harnesses' sign-in, setup and update flows moved into `useHarnessFlows`, which both use.
- UI: a multi-agent run, the threads one message started with several models, is one card in the work sidebar instead of a card per thread. Its mark shows how many threads it holds and the status that asks most of you, and its second line tallies them ("2 working · 1 done"). A click folds out a scoreboard of a line per model: what it changed (lines added and removed, less the turns you undid) and how long its lead took over the message, or that it's still working, needs you or failed. A line opens its thread, and hovering offers to archive it, to keep only the best answer. The scoreboard opens by itself while a thread of the run needs you or is open. Later and Archive take the whole run, and the inbox's cap counts a run as one card and archives it only whole. Threads started together share a `runId`, which `CreateThread` takes and `ThreadInfo` carries (`RPC_VERSION` 25); an older machine leaves them apart.
- The work sidebar is an archive-first inbox. Tabs above the list switch between Inbox, Drafts (shown while there are some), Later and Archive, with Drafts and Later counting what they hold; one menu beside them scopes the lists to a project and marks the inbox read. Each thread is a two-line card: its title and age over "Needs you" or "Failed" when it asks, its project, its worktree's branch and its harness, with its status on the project's badge, and it no longer sits under section headings: what needs you comes first, then pinned threads, then the rest, newest first. Hovering a finished thread offers Later and Archive in place of its age (H and E while it has focus); in Later and Archive, Back to Inbox (U) brings it back. Later puts a thread off until 8:00 tomorrow, and its card says when it returns; it comes back by itself then, or sooner if it needs you, and starts its group from that moment. The inbox keeps 8 threads: as a new thread starts, the oldest that are finished, read, unpinned and not open in a tab go to Archive, with a note that offers Undo for six seconds; one in a worktree or on another machine is left alone. The list follows what you open: a draft shows Drafts, a thread opened from the palette shows its own list, and the list chosen stays across window sizes and reloads. `@cerium/rpc` (version 24) adds `SetThreadLater`, and `@cerium/protocol` `laterUntil` on `ThreadInfo`; archiving a thread ends its wait.
- Reply to a passage of an agent's response: select text in it and a Reply button appears by the selection, which opens a comment box there. Each comment joins the message box as the quoted passage with your remark under it, editable or removable until you send, so one message can answer several exact points. The agent reads each as a Markdown quote followed by the comment, before the message's own text. Comments stay with the thread's draft, and follow it to the account's other devices.

- Muse is back. The backend loads the Muse adapter again, and the composer, model pickers, sidebar and Harnesses settings offer Muse. Where `muse serve` says it can't sandbox commands, as Muse 1.4.8 to 1.4.12 do on Windows even with the sandbox set up ([muse-code-sdk#107](https://github.com/meta-models/muse-code-sdk/issues/107)), a new thread with a Muse model offers only Read only and Full access. The probe reads this from the handshake of the `muse serve` it already starts for the sign-in check. `@cerium/protocol` adds `HarnessLimit`, sent as `limit` on an installed harness (`RPC_VERSION` 21). - The UI no longer uses the generic sparkle for anything "AI": each place shows an icon for what it does. What's new shows a scroll of notes, the buttons that write a commit message, pull request or issue show a pen, the effort router's Auto shows a route, the mark on files a thread's agents changed is a pencil, and the automatic title model is a bolt for "the quickest".
- An experimental effort router (Settings → Agents → Effort router, off by default). Before each turn of an agent on Auto, TypeSafe's Jev 1.13, through OpenRouter's Decisions API and your own OpenRouter key, reads the message (up to about 4,000 characters), the last two exchanges (about 1,000 each) and how the previous turn went (who sent it, tool calls, time taken, failure, files changed), and picks any reasoning effort the model offers. Cerium applies the most probable level when Jev is at least 50% sure; below that, after 1.5 seconds without an answer, or on an error, the level stays. Models that keep their prompt cache across an effort change, marked `cacheSafeEffort` on `ModelInfo`, are routed every turn, others only on a new session's first turn. For Claude these are the models measured to keep it (Opus, Sonnet and Haiku 5.5 and Fable 5.1). For Codex they are the models OpenAI's catalog lets take an effort change as a `configuration_update`, as Codex itself decides (`supports_reasoning_effort_updates` in the `models_cache.json` under the `codexHome` its app-server reports), so GPT-6 models a plan offers beyond Luna count too; without a readable catalog, GPT-6 Luna, the one measured, does. While the router is on, the message box's effort picker has an Auto switch and, on Auto, reads "Auto" beside the router's icon, with no level's bars and no level marked on the slider, as the router picks one each turn; new threads start on Auto, and picking a level by hand takes the thread off it; a setting decides whether agents a lead on Auto starts without naming an effort are routed too or run at the lead's level. Each response's header shows "Auto · level" beside its model as soon as the router decides, before the response starts, with the confidence, time and cost of the decision, or why the level was kept, under the pointer (a turn a child's result begins shows it where that turn starts); the agent panel says Auto; Settings shows this month's and all-time spend. The key is typed only into the desktop app of the computer whose agents use it, checked with OpenRouter, kept with the system's encryption (`safeStorage`), sent only to OpenRouter and shown by its last four characters; another device sees that there is one and can remove it, which also turns the router off. `@cerium/rpc` (version 23) adds `EffortRouterStatus` and `RemoveEffortRouterKey` on the machine, `SaveEffortRouterKey` on the device only, `autoEffort` on `SwitchModel` and `CreateThread`'s lead, and `@cerium/protocol` the `EffortRouted` event, `AgentInfo.autoEffort` and the `effortRouter` setting.

### Fixed

- Internal: `bun run ui open --light` (and `--dark`) shows Cerium in that mode. The flag only emulated the system's colour scheme, which the app follows only while its own theme is "System", and the tool's fresh browser profile starts it on Dark. In a browser of the tool's own, the flag now sets the page's stored theme to match and reloads it once; an `--attach`ed app's theme is left alone.
- UI: a reply streaming in a long thread no longer keeps the window busy. Every few streamed words rendered the whole window again, every row of the inbox with its menu, dialog and tooltips included: about 65 ms each in a window listing 140 threads, longer than the gap between them, so typing, scrolling and the reply itself stuttered while an agent wrote. Now only the conversation renders, in about 18 ms. An event that changes nothing in the thread list, such as a tool call, no longer redraws the inbox either (about 58 ms down to 5). The React Compiler had been skipping about a hundred components, the transcript, inbox, message box, menus and tooltips among them: on Babel 8 it can't read a parameter with a default value, so `@cerium/ui` pins `@babel/core` 7.29.7, the Babel it's built for, and the window and the message box no longer hold the two expressions it couldn't compile.
- Backend: counting each thread's events and reading events of one kind no longer reads every event in the store. Signed in, the cloud copy counted every thread's events after each burst of activity, which held up the backend for about 0.1 s on a 1.7 GB store (streamed replies, terminals and agents' Cerium tools waited meanwhile); it takes about 7 ms now. Startup's reads of open questions and sent attachments, and the effort router's spend, take under 1 ms instead of about 90 ms each, and Settings → Cost's report about 7 ms instead of 130. Two indexes on `events` do it, which a migration builds once (about a quarter of a second on a 1.7 GB store).
- Backend: signed in, the cloud copy no longer holds up the backend longer the longer a thread runs. Each round found the thread's events from where the cloud's copy ends by sorting every event of the thread, screenshots and all, and did it twice, the second time to find none left: about 0.12 s each for a thread of 20,000 events, while streamed replies, terminals and agents' Cerium tools waited.
