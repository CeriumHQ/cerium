# Changelog

All notable changes to Cerium are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow
[Semantic Versioning](https://semver.org/).

## [Unreleased]

### Changed

- Package audit tests retain parser, artifact and credential-safety regressions while removing duplicate cases, generic package conformance examples and assertions tied to the vault's internal write mechanism.

- Artifact documents use HTML parser source locations for safe head insertion, and artifact discovery uses the transcript's Markdown grammar for nested fences, comments and indentation. Repeated discovery reuses bounded results and messages without artifact fences skip parsing.
- Project TOML edits use parsed keys and source ranges, worktree include rules use Git-ignore-compatible matching, and skill front matter uses YAML parsing for comments, escapes and block values.
- The remote MCP endpoint uses the official protocol server and stateless HTTP transport. Desktop credential storage uses Electron's asynchronous encryption APIs so operating-system credential prompts do not block the main thread.

- Branch search uses Base UI autocomplete semantics and keyboard navigation, with a separate keyboard-accessible action menu for the highlighted branch. Onboarding uses Base UI's modal focus management while preserving its step transitions and nested sign-in dialogs.

- Threads can reuse durable workspaces, choose a base or existing branch, start from a GitHub pull request, and record dependencies on another conversation. The message box's branch chip lists the project folder, a new worktree and every checkout, with the new worktree's form (from a branch, a thread, a pull request or an existing branch) in the same popover. The titlebar shows the open thread's branch with its changed, ahead and behind counts and failing checks; its popover holds the threads sharing the checkout, linked issues and PRs (pasted links are recognised as either), setup state and scoped diffs, and its menu moves the thread, manages checkouts or removes the workspace. A pull request's facts list the threads working on it. Idle conversations can move between checkouts with their history preserved. New workspaces survive archive and deletion, with separate cleanup that protects imported checkouts, running terminals and local or unmerged work. MCP exposes workspace inspection, PR linking and watching, review scopes and queued moves. Push returns promptly with an operation ID, supports a reviewed-head check, and separates agent CI notifications from PR monitoring.

- Subagent spawns use a minimal, collapsible thread line with real provider marks, live status counts and provider groups instead of bordered cards. Agent transcripts and right-click actions remain available.

- Click a subagent card or select a child in the agents panel to read its live transcript with the same messages, reasoning and tool details as the lead. Child transcripts have no composer, edit, restore or execution controls; Back to lead returns to the lead's conversation.

- Snapshots of work threads' folders keep their files in one object store instead of one per folder, so a file several worktrees of a repository share is stored once, and that store is packed in the background instead of growing by a file per version. A minute after the app starts, older per-folder stores move into it, each one's own copies removed only once the shared store holds every object; nothing is pruned, so every message can still be restored, and git run on a folder's store by hand still reads it. On one machine's 13 stores, 233 MB became 46 MB.
- Deleting a thread finds its messages in the search index through an index by thread instead of reading every message's text, about 15 times faster with 50,000 messages. The update rebuilds the search index once; search finds the same messages as before.
- Archiving or continuing a thread releases its browser preview once outstanding browser calls finish; archives and deletions from other clients do the same. Running agents keep their pages between calls. Hidden pages allow background throttling, keep at most four inactive pages warm, and close after five idle minutes; reopening restores bounded navigation history.
- Opening a conversation reads its recent compact page first; earlier messages load on demand, and reconnects read only missed events. Live words update a separate per-agent text overlay while settled transcript blocks and queued inputs are projected incrementally. Conversations keep a bounded mounted window while following long replies, reading back, finding text, stepping through prompts and jumping to artifacts; find searches message history without mounting it, including rewound versions. Deep first jumps read intervening bounded pages to preserve the event fold's context. Summaries, approvals, files, artifacts and run statistics keep their whole-thread state through filtered pages (`RPC_VERSION` 47).
- An overview watch sends changed threads instead of repeatedly transferring every thread. The shared, bounded watch covers names, archives, Later and approval changes, resets on reconnect, retains archived history, and keeps the original list RPC available for older clients. Metadata caches refresh only the row that changed, and approval summaries scan live agents once. `@cerium/rpc` adds `WatchThreadOverviews` and `WatchLocalThreadOverviews` (`RPC_VERSION` 46).
- Cloud uploads walk indexed event pages from their last acknowledged event, translating the relay's existing count cursor once on reconnect. Large histories avoid repeated OFFSET scans and sorts, while retries, legacy streamed deltas and database rewrites keep their place.
- Large code fences stream as a bounded preview and extend without reparsing their earlier lines. Closing a fence restores the full highlighted, foldable code, diagram, math or artifact; copying keeps its entire text.
- Consecutive tool calls, agent cards and user inputs group in linear time, so a long run no longer spends progressively longer copying its earlier rows.
- Thread history has bounded compact pages and a durable append cursor for reconnect catch-up, including late imports and tied event timestamps. Old compact rows are filled only as their pages are read, in small resumable transactions. Cloud reads can page within individual uploads; legacy full-history RPCs remain available for older clients and whole-history consumers.
- Editing and restoring messages, undoing or redoing turn files, and side questions read only the event kinds they use, keeping screenshot and tool output out of their history queries. Restoring reuses its planning history and reads only additions before rewinding.
- Quiet CI notices survive an app restart and reach the agent exactly once with its next turn.
- Agents use shorter, stable instructions and smaller worker tool sets. Informational messages and successful CI notices wait for the next turn; blocking requests and correlated replies wake their recipients. Parallel child results are batched, duplicate completion reports are suppressed, and automatic request chains have a per-thread budget.
- Browser checks capture images only when requested, return visual context and errors together, reuse unchanged captures, and require a specific defect and fix beyond two reviews of a target/state. The UI CLI now uses `shot` or `--shot` for explicit captures. Routine replies use Markdown; artifact instructions load when needed.
- Titles, summaries and side questions record their helper calls and reported usage against the provider/model that ran them. Unavailable token counts stay explicitly unreported, and Claude resumes no longer count restored cumulative USD estimates as new spend.

- Usage-limit policy helpers have a distinct filename from the Limits settings page, so their TypeScript declarations build together on Windows.
- Settings → Usage is now two pages under Providers: Limits, with each harness's limit cards, and Tokens, with the tokens and cost agents used. Each has its own Refresh and "Updated" time, and the rail's usage rings open Limits.
- The model menu sets the model's effort and speed in a panel beside its list instead of stacking them under it, so it no longer runs off the top of the window. Each effort sits on its own row, weakest first, with bars that rise with it. On a phone the panel goes under the list, with Auto beside the levels. Several at once moves into the menu as a switch at its foot, showing how many models are picked while it's on, so a chat can start several models too. The access button beside it now shows the access picked, Auto included, and its menu lists just the three modes, with no heading or descriptions. It explains a greyed-out mode only when there is one.
- On a phone, the message box's project and branch shorten to fit, the branch first, instead of sliding under the model chip.
- A response no longer opens with a header of its harness's mark and its model, which the message box already shows. For an agent on Auto, the level the effort router picked moves to the turn's footer as "High effort", beside its time and tokens, with how the router decided under the pointer ("Auto picked High", its confidence, time and cost, or why it kept the level), where it read "Auto · High" beside the model.
- A new thread shows its question plainly, without the frosted glass over it that the pointer polished and typing wiped clear: a heading centred over the message box, each line coming into focus in turn as the pane opens. A new chat no longer says that chats read and search the web and never change your files.
- The usage rings at the foot of the rail draw one arc per harness, its tightest limit, instead of a nested arc per limit; the tooltip still lists every limit and marks the one drawn. The arc is grey like the rail's icons, over a visible track of the whole limit, with a softer mark, and turns amber only under a quarter left and red under a tenth, where it turned amber at half.
- Settings → Roster no longer shows or edits a line under each model. Settings → Tools is now Advisor, tagged Experimental, and the Your MCP servers switch is gone: agents always get the MCP servers set up in each harness, as before by default (`includeUserMcpServers` leaves the settings).
- Settings → Harnesses: harnesses update in their own rows instead of a dialog, and Update all starts every harness with a newer release at once. A row shows "Updating to v1.4.13…" with Stop, then the new version once it's done, or "Update failed" with Try again; the arrow beside it shows the harness's own output, where it can still be typed into. Leaving Settings doesn't stop an update. The blue dot on a harness's icon is gone, and each row shows the harness's version (`v1.4.12 → v1.4.13` when a newer one is out) where it showed the plan. Muse Code updates itself when it starts and Cursor runs on the SDK that ships with Cerium, so neither has an update command to run.
- Website: the phone beside "Fixes CI while you're away" is redrawn as a real handset, upright with a metal band, black bezel, side keys, status bar and home indicator, and the screenshot sits inside the screen instead of running under its corners. Its "Fix failing CI" notification is now a Liquid Glass banner inside the screen, under the island, with the app icon, title, "now" and message laid out as iOS does, and it drops in as the phone scrolls into view where the browser supports it.
- Website: the hero's glass C reads as clear glass instead of smoked plastic. The light behind it now shows through undimmed where it reached the glass washed out to a milky grey, crisp studio highlights replace the even room's soft sheen, the glass is double-sided so its inner faces catch light, and its edge is a narrow polished round instead of a fat soft bevel.
- Website: the hero's five beams and their labels take each harness's own colour (Claude's clay, Cursor's silver, OpenAI green for Codex, a warm grey for OpenCode, Meta blue for Muse Code) instead of a band of the spectrum.

- Desktop: Electron is updated to 44.9.1 to address a security alert.
- Git: merging or rebasing a branch keeps both sides' `CHANGELOG.md` entries instead of stopping on a conflict there.
- CI: the commit message check reads only the subject of a pull request's squash merge, whose body GitHub fills with the branch's already-checked commits.
- CI: a pull request that adds or updates only the web UI's, the website's or the relay's dependencies packages for Windows x64 alone, in about 3 minutes instead of 7, since none of those dependencies changes what the other platforms' packages carry.
- CI: packaging leaves out the relay's and the website's dependencies, Cloudflare's runtime among them, which no package carries.
- CI: the Intel Mac app can be packaged on an Apple silicon runner, and its smoke test then starts it through Rosetta. It carries only Intel's native packages, as before.
- CI: the repository's `MAC_RUNNER` variable names an Apple silicon runner to package both Mac apps on. The larger `macos-15-xlarge` built each in under 3 minutes, where the Intel app had been the slowest job in most runs at 6 to 10 minutes on Intel, and out of the standard runners' queues, but it is billed by the minute even for a public repository and won't start without a budget on the organization. Without the variable each app is packaged on its own processor's standard runner, as before: on the standard Apple silicon runner the Intel app waited in the queue longer than the Intel runner takes to build it.
- CI: a stable release packages its Mac apps on the runners the nightlies use, so a release is built the way the nightlies before it were tested.
- CI: the Linux AppImage, .deb and .rpm are packed side by side instead of one after another, and the .rpm's smoke test in Fedora runs alongside the other two.
- CI: each nightly package uploads to the nightly's draft release while its smoke test runs, so publishing, the last step of every push to main, no longer fetches every package and uploads it again; it adds the shared update files and the web UI, then makes the release public.

### Added

- `bun run live-check --compare-usage` compares a short native harness turn with the same turn through Cerium, using the same model, effort, speed, folder and user connections.
- Remote MCP: Cerium is now a remote MCP server, at `https://cerium.nonlooped.xyz/mcp`, for managing your threads from any MCP client: Claude, ChatGPT, Grok, your editor or your own scripts. From there you can start threads on your computer, one per task, list them with their status, read their latest messages, and send their agents follow-ups. The app signs you in to Cerium on Cerium's own page, which names it and where it sends you back, before you allow it. A computer takes the server's requests only once you turn on Settings → Remote MCP there, which is off by default. That page also sets the access threads started over MCP get (Ask first by default) and lists the connected apps to disconnect. Messages sent over MCP say which app sent them ("Sent from Claude"), and connected apps start at most 12 threads per computer in half an hour.
- Continue in new thread, in a thread's menu, the command palette and the message box's `/` list: a long thread goes on in a new one on the same harness, model, effort and access, in the same folder, worktree and branch, and the old thread is archived. The new thread's message box holds a brief Cerium writes from what it already has, without asking a model: the thread's title, its first and last requests, the agent's last reply, its plan, and the branch with its commits, uncommitted files and pull request. Edit it and send, and the new session starts small: a thread whose session had reached 235k tokens went on at 45k, most of that the harness's own start. Resuming a long thread after its prompt cache expired writes its whole context to the cache again, and compacting still reads it once.
- The rail counts what's new on its places: Home shows how many inbox threads are unread or waiting on you, and Chat how many chats wait for an approval. The count turns amber while anything waits on you, and its tooltip says which is which ("2 unread · 1 needs you").
- A thread with more than one prompt marks each down the conversation's left edge, longer prompts with a longer mark. The one being read stands out as you scroll, hovering a mark shows what it asked, and clicking it brings that prompt to the top, loading older history first when it has to. Hidden on narrow and touch screens.
- The `cerium` command and `cerium://` links. `cerium .` opens a folder in Cerium as a new thread, `cerium "fix login"` starts a thread in the current folder with that prompt waiting in its message box, and a `cerium://thread/<id>` link opens that thread, in the running app or one it starts. Settings → General → Command line installs the command (a small launcher on the PATH: a folder added to your user PATH on Windows, a link in `~/.local/bin` on macOS and Linux) and removes it again; the installed app registers the `cerium://` scheme and keeps the command pointing at itself across updates. Copy link, in a thread's menu in the sidebar, the inbox and its tab, and in the command palette, copies the thread's link for notes and pull requests.
- Replies draw Mermaid diagrams (` ```mermaid `) in the window's own colours, light and dark, and LaTeX math (`$…$`, `$$…$$`, ` ```math `) as MathML; a diagram that doesn't parse stays as its source, a block still being written holds its place instead of flickering, and prose like "costs $5 or $6" stays text. Both libraries load only when a reply uses them.
- Settings → Notifications → Sounds: Cerium's own short sounds, off until chosen, for a thread that finishes (a soft two-note rise), an agent that needs you (two even taps) and a failure (a low two-note fall). They are synthesized, so nothing is downloaded, and play whatever the window shows, the thread open in it included, where the system's notification sound is heard only while you're away. Each has a Play button to hear it. Many threads finishing at once make one sound: the most important of the batch, and for 2.5 seconds after a sound only a more important one follows. The system's own sound switch is now called Notification sound.
- Side questions: `/btw <question>` in a thread's message box, the Side question entry in its `/` list, or Ctrl Shift / opens a pop-over over the box that answers a quick question with the thread's conversation in view, and follow-ups in it carry on. Nothing is kept: the question and its answer are no message in the transcript, nothing in the lead's harness session or its history, and nothing to its running turn, so it works while the lead is mid-turn (the answer is told the lead is still working). Closing the pop-over drops it all. Claude Code answers in a fork of the lead's session that is never saved (`forkSession` with `persistSession: false`), and Codex in an ephemeral `thread/fork`; both can only read, and a command or tool that would change anything is refused rather than asked about. Cursor, Muse Code and OpenCode have no fork that stays out of their history, so each answers a one-off completion (as titles do: nothing saved, no tools) told the newest turns of the conversation, up to about 6k tokens word for word and a note of how many older ones it leaves out; a fork that fails falls back to the same. `@cerium/rpc` adds `AskSideQuestion` (`RPC_VERSION` 44); `HarnessAdapter` adds an optional `sideQuestion`.
- Settings → MCP servers and Settings → Skills: every installed harness's MCP servers and skills for a project, each listed once with the logos of the harnesses that have it (dimmed where it's off, marked where its connection failed or needs sign-in), under This project, All projects and Built-in, with a search and a filter per harness that puts that harness's switch on each row. Opening one shows what a server runs and its secrets by name, each harness's copy with its config file, connection and switch, and a server's tools in a grid with a column per harness. Both are read from and written to, at user and project scope, the harness's own files (Claude Code's `.claude.json`, `.mcp.json` and `settings.json`, Codex's `config.toml` through its app-server, OpenCode's `opencode.json`, Cursor's `mcp.json`) with minimal edits that keep comments and layout. A server or skill turns off for one project where the harness can do that natively (Claude Code, Codex and OpenCode servers, Claude Code and OpenCode skills; Codex turns skills off for every project), and a single tool of a server where the harness can (Claude Code and Codex); where it can't, its line says so instead of offering a switch, and Codex's are held off with its own reason while it doesn't trust the project. Add to writes a server into a harness that doesn't have it in that harness's format, or a skill's folder into its, for this project or every one. Secrets never leave the harness's files: a server's environment variables and headers show as their names and whether each is set, and a copy leaves them empty, naming each for the user to fill in. `@cerium/rpc` adds `ReadHub`, `ReadHubStatus`, `SetHubServer`, `SetHubTool`, `SetHubSkill`, `CopyHubServer` and `CopyHubSkill` (`RPC_VERSION` 42).
- Open in your editor: a file chip, a tool call's menu, an edit's card, the Files panel and the file viewer open the file in VS Code, Cursor, Zed, a JetBrains IDE or Visual Studio, at the chip's line, where a read began, or the line number you click in the viewer. Clicking a file chip opens it there instead of showing it in File Explorer, which stays in its menu. Cerium finds the editors installed on the computer; Settings → General → Editor picks the one to use (the first found until then) or turns it off.
- Limit failover and auto-resume. When a harness's plan or usage limit runs out in the middle of a lead's turn, the thread does what it was set to: wait for the limit to reset and go on with the same harness and session, or go on at once with the next model on the roster from another harness, or stop with the error as before. The default is in Settings → General → Usage limits (Wait and resume to begin with), each thread overrides it in a last row of its model menu ("When usage runs out": Wait, Switch, Stop), and each automation picks its runs' threads' policy beside its access. Every adapter now reports a plan limit as one `LimitReached` event, apart from the momentary throttles that stay `AgentError`s, with the limit's name and reset time where the harness says (Claude's rejected limit and its reset, Codex's exhausted window from the plan's limits, Muse's quota, OpenCode's quota, Cursor's usage limit). A waiting thread's transcript says "Claude 5-hour limit reached · paused until 14:00" in one row and marks it resumed later; without a reported reset it tries again after 20 minutes, then 40, and stops after five pauses in a row. The pause is in the lead's history, so it survives a restart of Cerium: a reset that came while it was closed resumes the lead on start, and a pause ends once, whether the reset, the user's next message (sent at once) or stopping the agent gets there first. A switch hands the lead to the roster's first model from a harness that hasn't run out, with the same brief as a handoff plus the interrupted turn's tool calls, and a notice to carry on rather than start over; it never goes back to a harness that ran out since a turn last completed, and with none left it waits instead. A child that runs out of usage reports so to its lead, and the thread's own policy applies to leads only. `@cerium/rpc` (version 44) adds `SetThreadOnLimit`, an optional `onLimit` to `CreateThread` and to automations, and the threads store a new `on_limit` column; `Settings` gains `limits`.
- Agents run the project: the `project_run` tool starts, stops and restarts the thread's run (or setup) in the thread's own terminal, where the user watches it, and answers with how it stands (running, exited with its code, or stopped), the first local address it printed and its last lines of output as plain text (200 at most). A start waits up to 15 seconds for the run to print its address or end, and the lead is then spared the notice of what the caller was just told. It asks as a command would: a read-only agent is refused, auto and full access go ahead, and the user is asked in the other modes. It runs only a command the user saved or the project's `.cerium.toml` holds, never a guess. Leads and their children can use it, and the lead's instructions point to it. Cerium never opens the served page in the thread's browser on its own: that browser is the user's to watch, and may be on another page, so an agent opens the address it is told with `browser_open`.
- A thread's lead hears where the project's run serves: the first time the run's output prints a local address (`http://localhost:5173/`; a server that prints `0.0.0.0` is told as `localhost`), the lead gets a notice with it, once per run, to open in the thread's browser. When a setup or a run fails, its notice carries the last lines it printed, as plain text (30 lines, 3,000 characters at most), in place of only its exit code. A run replaced by another, by pressing Run again or by an agent, is no longer told to the lead as stopped. The run's notices never start a turn on their own, since a turn costs the user's plan: an idle lead hears them with its next turn, where a newer notice of the run replaces an older one it hasn't heard, and a lead mid-turn hears them as it goes. A setup's ending still wakes the lead, which waits on it.
- Project actions and a project scripts card that reaches every project. Settings → Git & GitHub → Project scripts now has a project picker, opening on the project of the thread Settings was opened from, where only the most recently used project could be edited before; each command says where it comes from (this machine, the project's `.cerium.toml`, or Cerium's guess) in a word, with what that means on hover, in place of the paragraph above it. A project can have named actions beyond Setup, Run and Teardown (Test, Lint, Migrate): they sit in a menu beside a work thread's Run button and in the command palette, and each runs in a terminal of the thread's own, labelled with its name, which the terminal drawer opens on. Save keeps the commands on this machine; Save to .cerium.toml writes them into the project's file (made if missing) so its team shares them, keeping everything else in it as it was and clearing what was saved here, which would have shadowed it. The file holds the actions in an `[actions]` section, a `name = "command"` each, beside `[scripts]`. Commands with quotes or backslashes in them now read from the file and write back to it. `@cerium/rpc` adds `WriteProjectScriptsFile` and `RunProjectAction` (`RPC_VERSION` 40), an optional `actions` to `SetProjectScripts` and to `ProjectScripts`' result, and the store's projects keep the user's saved actions in a new column.
- Worktrees that boot. A new worktree gets the files git ignores that the project needs, copied from the project before setup runs and again when an archived thread is restored: what the repository's `.worktreeinclude` lists (gitignore's syntax, as other tools read it), or without one its `.env` and `.env.*` files. A copy never replaces a file the worktree already has, and the lead is told which files came across. A work thread's scripts and terminals get `CERIUM_PORT`, the first of ten ports no other thread has (free when the thread was given them, kept for its life), `CERIUM_ROOT_PATH` (the project's own folder), `CERIUM_WORKSPACE_PATH` (the thread's folder), `CERIUM_BRANCH` and `CERIUM_THREAD_ID`, so each worktree can run its own dev server and database; the thread's lead is told its ports in the setup notice. A third command, `teardown` (a `teardown = "…"` in `.cerium.toml`'s `[scripts]` or saved for the project), runs out of sight in the worktree when its thread is archived or deleted, after its agents end and before the worktree is removed, for 60 seconds at most; one that fails or runs out of time doesn't stop the archiving, and the window says so with the end of its output. It never runs from a guess. Settings → Git & GitHub has a Teardown field beside Setup and Run. A setup Cerium only guessed still never runs by itself: the thread asks above its message box to run it once or always for this project (which saves it as the project's setup), and the lead's notice says the user was asked. `@cerium/rpc` (version 39) adds `teardown` to `ProjectScripts` and `SetProjectScripts`, which now leaves out a command it should not change, and `SetThreadArchived` and `DeleteThread` answer with the teardown's failure.
- A Desktop theme in Settings → Appearance (the desktop app): the window's glass takes its tint from the wallpaper and its accent from the system's accent colour, and follows both as they change. On Windows the wallpaper's own colour is read, or the desktop's colour when it has no picture; on macOS and Linux the accent colours both. Any status colour the accent would be mistaken for (a blue accent and "running", say) turns aside from it, and the theme's sample shows the window frosted over the wallpaper itself. Two new glasses join it, Forest (green Waldglas) and Amethyst (sun-purpled violet), and the themes now run Cerium and Desktop first, then the glasses round the spectrum from Cranberry to Amethyst, in rows of three; the welcome's glass step shows all eight glasses.

- Old threads are slimmed: once nothing has happened in a thread for a week, its screenshots are removed, and the space goes back to the disk. Those were most of a long-used database; messages, tool calls and their text output stay whole, and a removed screenshot shows as "Image removed" in its call. Settings → General → Slim old threads picks after a day, 3 days, a week, 2 weeks or 30 days, or never. It runs a minute after the backend starts, every six hours and soon after the setting changes, a few tool results at a time, so the app carries on meanwhile; the first time a lot is freed the database file is rewritten once, on a thread of its own, and in small steps from then on. A thread that picks up again is slimmed again once it goes quiet.

- Anonymous crash reports, to Sentry, from release builds. What gets reported: a view that couldn't be drawn and errors nothing in the window handled; a backend that couldn't start (its database, its migration, its port) or crashed, natively too; a harness session that failed to start or failed while running (not a harness that isn't installed or signed in, nor one stopped on purpose); the relay closing the connection with a code of its own or sending a message this build can't read; and an update check or download that failed for a reason other than the network. Each report carries the error's type, its message with file paths, web addresses, emails, IP addresses, ids and quoted prose removed, its stack with only where in Cerium's own files each frame ran, and a few named facts (the harness, the phase, a close or error code). With them come Cerium's version and channel, the system and its version, and the processor. Never messages, files, folder or project names, thread titles, the account, the machine's name or IP address, breadcrumbs, screenshots, local variables or native memory dumps. Only the desktop shell sends reports: the UI and the backend hand it theirs, and `apps/desktop/src/scrub.ts` decides what each may carry. The same failure is sent once in ten minutes, and a run sends at most thirty. Settings → General → Send crash reports turns them off; builds without a DSN (development, forks, pull requests) send none. The release workflows read the DSN from the repository's `SENTRY_DSN` variable.

- A crash guard: a view that throws while drawing no longer blanks the window. A conversation that can't be drawn gives way to "This view couldn't be drawn" with Try again and Copy details, while the sidebar, the tabs and the thread's message box carry on; a pane that throws takes only its pane, and anything that throws outside every pane shows "Cerium hit a problem" with Reload, Copy details and the logs folder. Copy details holds the version, the system, the error's stack and the views it was drawn in.
- When the desktop app's backend stops, the window says why instead of only "Reconnecting to Cerium's backend…": it couldn't open its database, couldn't update the database for this version, couldn't open its local port, couldn't start, crashed, or exited with a code, with the reason in one line. Restart starts it again at once instead of after its back-off, Logs opens the logs folder, and Copy details holds the reason with the end of the backend's log.

- Auto is a switch beside the effort levels in the model menu, rather than one of them: picking a level no longer takes a thread off Auto, and while Auto is on the picked level shows dashed, the one a turn falls back to when Jev doesn't answer in time, gives no usable answer, is too unsure to pick a level, or can't tell what the turn asks for. The levels the router picks hold for the session and no longer replace the picked one, which until now became whatever the router last chose, often Extra high, with nowhere to see or change what an unsure turn would use. A turn's Auto note says "Fell back to High" when it did. The same switch sits in automations' model menu.

- Settings → Appearance → Window has an opacity slider (Windows and macOS) for those who would rather not see the desktop through the window: at the left the theme keeps its own glass, at the right the window is solid.

### Changed

### Fixed

- CI: the file-watcher test waits for both expected paths across batches, avoiding a timing failure on busy Windows runners while still checking ignored paths and Git status.
- Read-only Codex agents can start again: the app-server handshake enables the capability required by their granular approval policy, preserving read-only sandboxing and MCP approval prompts.
- A new thread asks its question again, with the message box seated under it in the middle of the pane. Since subagent conversations became viewable, the open thread's views sat in a box as tall as the pane, which pushed the question out of sight and dropped the box to the foot.
- CI: the Fedora RPM smoke test waits until the runner allows unprivileged user namespaces, after the Debian package tests its AppArmor profile. Starting it earlier raced that setup and could abort Chromium on Linux Arm64; it still runs alongside the AppImage test.
- An agent's push always lands on a branch of its own name. A branch cut from `origin/main` tracks main, and the push followed that tracking, so a feature meant for a pull request went straight to main; such a push now goes to its own branch and points the tracking there.
- A thread started in a new worktree shows at once, with its message, instead of vanishing for up to a few minutes. Its worktree is checked out behind it, and its agent starts once the folder is ready; a worktree that can't be made says why in the thread. Copying the ignored files a worktree takes (`.env`, or what `.worktreeinclude` lists) no longer walks every ignored folder: git did that through node_modules, following bun's workspace links on Windows, and it took 42 seconds in Cerium's own repository, where it now takes a fraction of one. Ignored folders are looked into only for lines with a slash that name something inside them. A thread whose worktree is missing when it picks back up (Cerium quit while making it, say) gets it back, with setup run again.
- Deleting or archiving a thread with a worktree takes a moment instead of minutes. Its folder moves aside and is deleted in the background, where `git worktree remove` took almost 2 minutes over a worktree's installed dependencies, stopped at node_modules' long paths, and then was retried three times. What a removal leaves behind is cleared when Cerium next starts.
- Archiving or deleting a thread with a worktree takes it off the list at once, and it no longer waits on its folder. A process still running in the worktree (a dev server an agent left behind, say) stops Windows moving the folder aside, and Cerium then deleted it, dependencies and all, while the thread waited minutes and usually failed anyway. Now git lets go of the worktree and its branch at once, and the folder goes in the background once whatever holds it ends. Restoring the thread meanwhile waits for it, then checks the worktree out again. The list puts a thread back only if archiving or deleting it fails.
- Settings → Git & GitHub → Project scripts edits any project, not only the most recently used one.
- Scrolling and opening or closing the sidebars no longer stutter in a thread an agent has written a lot in. Each word an agent writes fades in, and that fade never let go once it ended: every word kept a live animation and a blurred shadow, 1,800 of them in one long thread, which each scroll, sidebar toggle and new word restyled and repainted. A word now drops its fade once it lands; in that thread a sidebar toggle went from 7–8 dropped frames to 1–2, and scrolling from 11 to none.
- On Windows, a terminal whose shell exits and every read of Cursor's limits (one every five minutes) no longer leave a `conhost.exe` running for as long as the backend runs: node-pty never closed the console of a process that ended, so a day of use piled up hundreds of them. Pseudoterminals now run on the ConPTY node-pty ships, which closes its console when the process ends.
- On a Mac, Option with a digit types again: Go to a tab took ⌥1–9 everywhere, so a British layout couldn't type `#` (⌥3) and a German one `[ ] | { }` in the message box or any other field. In the Mac app it is ⌃1–9 now, and wherever it is still bound to Option a character the Option layer types in a field wins. Open tasks, Open GitHub and Open automations default to ⌥⌘3, ⌥⌘4 and ⌥⌘5 there, since ⌘⇧3–5 take macOS screenshots. The terminal's Option key types the Mac's own characters, as Terminal.app's does, instead of acting as Meta. Shortcuts rebound in Settings → Keyboard keep their keys.
- On a Mac, terminals, project scripts and harnesses run in a UTF-8 locale. An app the Dock or Finder starts gets no `LANG`, so its shells ran in the C locale: typed accents and emoji showed as escapes like `<ffffffe9>`, and `ls`, `git` and `less` printed Unicode names as `?` or `<E9>`. The backend now starts with the system's language and region in UTF-8 (`en_GB.UTF-8`), or `en_US.UTF-8` where macOS has no such locale, unless the environment already names one.
- A path an agent writes from the home folder, such as `~/.zshrc`, opens, reveals and copies as the file in the home folder the thread's folder is in (`/Users/<name>`, `/home/<name>`, `C:\Users\<name>`), instead of as a `~` folder inside the thread's folder that doesn't exist. Outside a home folder it no longer offers a place it can't tell.
- On Linux and macOS, Claude Code, Codex, OpenCode, Muse, the Cursor CLI and `gh` are found without the `which` program, which Arch's base system, minimal Fedora and many containers don't install: there every harness showed as not installed, and GitHub as missing its CLI, with nothing saying why. Cerium now reads PATH itself, taking each executable file of the name in PATH's order, as `which -a` did.
- On Linux, the OpenCode server Cerium shares for models and sign-in, and the Cursor CLI it asks for usage, no longer run in `/tmp`, which every local user can write to: an `opencode.json` or `.cursor` folder another user left there would have loaded, and the Cursor folder was started with `--trust`. They run in `cerium` in the user's runtime folder (`$XDG_RUNTIME_DIR`), or in `~/.cache` without one, made for that user alone. Windows and macOS keep the system's temp folder, which is the user's own there.
- Showing a file in its folder says where it goes on each system: Show in Finder on a Mac and Show in its folder on Linux, where every menu and button said Show in File Explorer.
- CI: a pull request's Mac app is signed ad hoc, so its packaging check passes. electron-builder signs nothing for a pull request unless told to, which left Electron's own signature on a bundle it no longer matched, and the smoke test's `codesign --verify` refused it; a pull request now signs ad hoc whatever certificate the repository has, so its build holds no secret and waits on no notarization.

Before each turn of an agent on Auto, TypeSafe's Jev 1.13, through OpenRouter's Decisions API and your own OpenRouter key, reads the message (up to about 4,000 characters), the last two exchanges (about 1,000 each) and how the previous turn went (who sent it, tool calls, time taken, failure, files changed), and picks any reasoning effort the model offers. - A message an agent sends to an agent that isn't running is refused with the reason, instead of being dropped while the sender heard it was delivered.
- A turn its harness refuses to start now ends with the reason in the thread, instead of leaving the agent working for good with nothing to stop.
- UI: nothing clears the message box any more. Drafts are kept in the window's storage, so they survive a reload or restart, reconnecting to the backend, "Connecting to …" while another computer answers (the box now stays, keeps taking writing, and lets you send once it answers), the web app moving to another version, and the window turning phone-narrow. A reload also comes back to the thread or draft that was open, and pasted files waiting in a draft are kept for 30 days instead of one.
- Nightly releases are named with a padded build (`0.2.0-nightly.n000014` instead of `0.2.0-nightly.14`), so GitHub's release list, which orders a day's releases by tag as text, puts the newest nightly first instead of an older build whose number reads larger as text (build 9 above builds 12 and 13).
- UI: a reply streams into a long thread with about half the work per word. Only the part of the conversation that changed renders again, instead of every earlier message, tool call and card for each streamed word.
- Opening a thread reads its history about three times faster: the provider's original messages, kept in the store but never shown, are no longer read and parsed with it. In a thread full of screenshots that was most of the data.
- Agents at work no longer slow the backend down as threads pile up: the thread list it re-reads after every event, for the inbox, the cloud copy and whether anything is working, takes two reads instead of one per thread (about 6× faster with 300 threads).
- Your other devices now see the version a computer runs after it updates, instead of the one it signed in with: each device reports its build every time it connects to Cerium's cloud.
- Threads from a newer version of Cerium no longer disappear or fail to open on another device: an access mode, agent state or other value a version doesn't know reads as a safe fallback (an unknown access mode as Ask first), and threads or events it can't read at all are skipped instead of failing the whole list or ending the live feed.
- A long draft no longer hides the end of the conversation: the transcript keeps room for the message box at whatever height it grows to, and the jump-to-latest button sits just above it.
- Cursor: turns in long workspace paths on Windows (chat threads, temp and deeply nested folders) now finish. The SDK could not save their conversation there, so a turn never ended and Cursor replayed it, commands and all, every half minute; those workspaces now keep their agents in files the SDK can write, and a run still going 15 seconds after its turn ended is stopped.
- Muse: on Windows, before its sandbox is set up, Ask first, Accept edits and Auto sessions say so (in the thread and to the agent) instead of failing every command and retrying for minutes. The fix is a one-time `muse sandbox windows setup` in an administrator terminal, or Full access.

- Desktop: Acrylic now shows through the window (the window is transparent), with edge resizing, Snap and Windows 11 rounded corners restored natively since Electron removes them from transparent windows.
- Claude adapter: trusted bus tools are approved inside the permission callback instead of through `allowedTools`, which bypassed the callback and triggered an SDK warning.
- `@cerium/rpc`: events reach the UI without the provider's original message, which isn't always strict JSON and ended the live event stream.
- UI: the message box no longer draws a second focus outline inside the composer's own focus border; components with their own focus style can opt out of the global ring.
- UI: picker labels in the composer stay on one line when space is tight.
- UI: logos of harnesses that can't run dim the same way whether the logo is in colour or not, in the sidebar and the model picker.
- UI: costs under a cent read "<$0.01" instead of "$0.00", and the inspector's latest message preview is plain text instead of raw markdown.
- UI: a thread whose lead has stopped or failed no longer offers a message box that can only fail; the composer says so and offers to start a new thread. Approval cards it left unanswered read as expired instead of offering buttons, and tool calls cut off mid-run read as interrupted instead of spinning forever.
- UI: the inspector only offers what an agent can do: "Message" moves to the composer for a live lead, "Interrupt turn" is only enabled mid-turn, and an agent that has stopped or failed has no actions. The "Open" button, which did nothing, is gone until agents get their own views.
- UI: stopping an agent from the inspector asks first, and says what stopping costs: a stopped lead ends its thread.
- UI: the inspector says "Just now" instead of "now ago", and an agent with no usage yet reads "None yet" instead of zero tokens and an unreported cost.
- UI: an empty sidebar explains where threads or chats will appear, and project groups use a plain folder icon, since a work folder needn't be a git repository.
- UI: the thread title in the titlebar is plain text instead of a button that opened nothing, so it drags the window like the rest of the titlebar.
- UI: the browser preview stands a light backdrop behind the light theme instead of the dark one.
- UI: notice bars carry a faint tint of their status colour, so they read as banners rather than stray lines over the transcript.
- `@cerium/orchestrator`: read-only agents no longer wait on approvals: Cerium approves their requests itself (web searches and fetches, reads outside the folder), for every provider, since each harness already keeps them from writing. These requests are never shown, not even briefly. Tools of the user's own MCP servers still ask.
- `@cerium/orchestrator`: stopping a subagent tells its lead, which otherwise waited for a result that would never come.
- Claude adapter: a permission request is ready for its answer before it is announced, so an immediate answer is no longer lost.
- UI: approval requests from subagents appear in a tray above the message box, one card per waiting agent with who is asking and how many requests are queued, and in the agent inspector when the subagent is selected. Before, they were counted as "Needs you" but could not be answered anywhere. A subagent's card in the transcript also says "Needs you" instead of "Working" while it waits.
- UI: a child agent's report or another agent's message longer than one line folds behind its first line, and opens as rendered markdown instead of one run of raw text.
- UI: typing `$` no longer flashes the files and folders an earlier `@` found while the skills load.
- Sending a message no longer leaves it unseen while the agent starts or finishes its turn: a new thread opens at once while its harness session starts behind it, and a message sent mid-turn shows as queued right away. A lead whose session never started gets a new one on the next message, and messages it never delivered go with it instead of being lost.
- Remote control: "Can't reach …" no longer shows for every dropped line. Coming back to the app, a network coming back or a computer waking checks its connection to Cerium's cloud at once and reconnects within seconds, where a dead connection could go unnoticed for up to 70 seconds; a tunnel to another computer counts as connected only once that computer answers; and the warning waits 8 seconds of being disconnected before it shows.
- Muse adapter: Muse follows the thread folder's `AGENTS.md` and loads its skills, as the other harnesses do. It had skipped both, treating every folder as an untrusted workspace.
- `bun run dev` starts the desktop shell from inside a tool that sets `ELECTRON_RUN_AS_NODE`, which it no longer passes on; serves the UI on the first free port from 5173, written to `.cerium-dev/ui-url`; and reuses this checkout's dev servers when they already run instead of starting a second set.
- `tsc -b` no longer type checks the backend's git-ignored scratch scripts (`apps/backend/scripts/_*`), so a stale one can't fail `bun run verify` on a clean checkout.
- A thread that was messaged after its lead finished no longer sits on "Working…" for minutes. Cerium ran at most six turns at once per harness for Claude Code and Codex (four for Cursor, Muse and OpenCode, twelve across every harness), so with more threads busy than that, a lead woken by a message queued until another thread's turn ended, and any thread messaged after it queued too. A child waiting on its lead to answer a permission request could even hold the turn its lead needed. Turns now start as soon as their messages arrive.
- Remote control no longer drops the computer over and over while a long thread opens, and opens threads in a fraction of the time. A thread's history came as one message holding every screenshot its agents had looked at (tens of MB in a busy thread), which Cerium's cloud couldn't hold: it cut the computer's connection, the phone asked again, and so on. History now leaves those images out and the transcript reads each one when it shows it, so a 43 MB thread opens as about 1 MB; the cloud copy of threads leaves them out too. `@cerium/rpc` (version 12): `ThreadEvents` takes `withoutImages`, and `ToolImage` reads one such image.
- Remote control: messages between your devices go through Cerium's cloud in pieces of at most 256 KB, so a big answer, such as a large file or a thread's history, is never too big for the cloud to pass on and never cuts the computer's connection. `@cerium/protocol`: tunnel frames carry `more` on `Send` and `Receive`; an end that sends pieces sets it on every frame, and only such ends are sent pieces, so older versions keep getting whole frames.
