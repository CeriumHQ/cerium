# Changelog

All notable changes to Cerium are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow
[Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- Bun workspace with Vite+ for build, lint, format and test, TypeScript 7, and Effect language service diagnostics.
- LF line endings enforced for every checkout via `.gitattributes`.
- Apache-2.0 license.
- `bun run vendor:effect` fetches the pinned Effect source as a reference for coding agents.
- `@cerium/protocol`: canonical agent events, capability manifests and harness status schemas.
- `@cerium/harness`: the adapter contract every provider implements, plus version range checks.
- Claude adapter: translates Claude Agent SDK messages into canonical events, tested against a recorded session.
- Claude adapter: detects the installed Claude Code version and login status, and runs live sessions with approvals, file change tracking, per-turn usage, and mid-session model and effort switching.
- `@cerium/protocol`: orchestration events (turn inputs, spawned agents, agent state, spawn approvals) and the rule that a child's access only narrows.
- Claude adapter: reports completed reasoning blocks alongside streamed reasoning.
- `@cerium/protocol`: thread and agent record schemas.
- `@cerium/store`: SQLite persistence for threads, agents and the append-only event log, using Drizzle on Node's built-in `node:sqlite` with generated migrations and an FTS5 startup check.
- `@cerium/store`: per-thread event history, and stopping agents a previous run left live.
- `@cerium/store`: a `settings` table that keeps the user's settings as JSON values by key.
- `@cerium/protocol`: the user's settings the backend applies, starting with whether sessions load the user's own MCP servers.
- `@cerium/orchestrator`: the user's settings, saved in the store and read when a session starts; a stored value that no longer decodes falls back to its default.
- `@cerium/harness`: sessions can mark injected MCP servers as trusted so their tools skip approval prompts.
- Claude adapter: trusted MCP servers' tools run without permission prompts.
- `@cerium/orchestrator`: threads with a lead and depth-1 children; inbox delivery that batches notices into one turn and never interrupts a running turn; per-provider and global concurrency caps; catalog spawns with access narrowing and user approval for other models; lead/child/cross-thread messaging rules with per-pair budgets; child results delivered to the lead; persisted, live-streamed event log.
- `@cerium/orchestrator`: tracks which threads wait on the user's approval, serves thread history, and stops agents left live by a previous run at startup.
- `@cerium/bus`: Cerium's MCP server on a loopback port, injected into every session with its own bearer token, exposing `list_models`, `spawn_agent`, `list_agents`, `list_threads`, `send_message` and `kill_agent`.
- `@cerium/rpc`: the RPC contract between the UI and the backend: thread overviews, thread history, a live event stream, harness status, and actions to create threads, send messages, answer approvals and spawn requests, and interrupt or stop agents.
- `@cerium/rpc`: reading and changing the user's settings.
- `@cerium/backend`: composes the store, orchestrator, Claude adapter and MCP bus into one layer, with a live check where a Claude lead spawns a Claude child through the bus and relays its answer.
- `@cerium/backend`: an entry point serving the MCP bus and the UI's RPC endpoint on one loopback port; the RPC WebSocket only upgrades for this launch's token. `bun run dev:backend` runs it with a development data folder and writes the connection details for the UI.
- `@cerium/ui`: React app with Cerium's design tokens (monochrome translucent glass over Acrylic, with colour reserved for status and provider logos; dark and light themes) and the window frame: a titlebar over the thread sidebar and the transcript, with the agent inspector opening beside it on demand from a titlebar control that shows the thread's agents.
- UI: thread sidebar with collapsible project groups, colour-coded thread status, official provider logos (in their own colours where available) for active multi-agent threads, relative times, and harness status in the footer.
- UI: thread transcript built from canonical events: user messages and markdown replies (streaming-safe) under one header per response, collapsible reasoning, compact grouped tool calls with inputs and outputs, chips for spawned agents, child results inline in the lead's response, inline approval cards, and per-turn usage.
- UI: composer floating over the transcript, with grouped model picker (provider logos), reasoning effort and access mode pickers, Enter to send and a stop button while a turn runs.
- UI: separate Work and Chat modes, switched from the titlebar; the sidebar lists only the active mode's threads, work grouped by project and chats by recency.
- UI: agent inspector: the lead and its children as a tree with colour-coded state, the selected agent's model, effort, access, tokens, cost and latest message, actions to open, message, interrupt or stop it, and the thread's usage per provider.
- `@cerium/desktop`: Electron shell with Windows Acrylic behind the UI, Windows' own caption buttons over the custom titlebar, a sandboxed preload, and links opening in the browser. `bun run dev:desktop` runs it against the UI dev server.
- UI: inside the Electron shell the titlebar reserves exactly the caption-button area Windows reports, and the window tint is lighter so the real Acrylic shows.
- UI: Cerium's "Prism C" mark in the titlebar and as the favicon.
- Desktop: the UI can open Windows' folder picker to choose where a work thread runs.
- Desktop: the UI can set the window's theme; Windows tints the Acrylic and draws the caption buttons to match, and "system" follows Windows' own light or dark mode.
- UI: an Effect RPC client for the backend, wired into atoms: thread overviews and harness status that refresh as agents work, and each thread's history merged with its live events. In development the UI dev server hands the page the backend's connection; after a backend restart the client reconnects and picks the live feeds back up.
- UI: runs on live backend data: the sidebar lists real threads with their status and the installed harnesses; the transcript streams the open thread's lead and answers its approval cards; the composer starts new threads in a chosen folder with the picked model, effort and access (unavailable harnesses greyed out) and then messages the thread's lead; the inspector interrupts or stops agents; a slim notice reports a lost connection or a failed action. The hand-written fixtures are gone.
- UI: the transcript follows new output while you're at the end, stays put while you scroll back to read, and returns to the end when you send a message.
- UI: a "Jump to latest" button appears above the composer while you've scrolled back, and glides to the newest output.
- UI: a shimmering "Working…" line shows the lead is busy while nothing else on screen moves: before its first output and between steps. A reasoning block shimmers while it streams.
- UI: an approval card for a file edit shows the change as a compact diff, so it can be judged before it's allowed, and an edit's tool row expands to the same diff instead of raw JSON.
- UI: the composer keeps a draft per thread (and per mode for a new one), puts the cursor in the message box when a thread opens, gives back a message that failed to send, and stops a running turn with Esc. The access menu shows each mode's icon, and the placeholder no longer promises @ mentions that don't exist yet.
- UI: a new thread starts with the model, reasoning effort and access the last one was given, as it already did with the folder.
- UI: the sidebar folds away from the titlebar or with Ctrl B (remembered across launches), leaving a new-thread button in the titlebar; Ctrl N opens a new thread and Ctrl J toggles the agent inspector, as their tooltips promised.
- UI: settings, opened from the sidebar's gear or with Ctrl ,: the sidebar turns into the list of categories and the main panel shows the open one. Esc or "Back to threads" returns to the thread exactly as it was left, scroll position and draft included.
- UI: Appearance settings: the theme (system, dark or light), picked from miniatures of the window drawn in each theme, and the conversation's text size, previewed on a sample conversation as the slider moves.
- UI: Agents settings: the lead model for new threads, picked from the models of each harness that can run; its reasoning effort on a rising gauge that says what the chosen level means; the access a work thread's lead starts with, each mode showing what it may read, edit and run; and whether agents also get your own MCP servers, with a diagram of where their tools come from. The composer offers the same model, effort and access, so a change in either shows in both.
- UI: Harnesses settings: each harness's installed version and whether Cerium has tested it, how you're signed in and where it's installed; when one needs you, its own login command to copy or how to install it. "Check again" probes them afresh, and the harness icons at the foot of the sidebar open this page.
- UI: Keyboard settings: whether Enter or Ctrl Enter sends a message (the other way of pressing Enter starts a new line), with a box to try it in whose keycaps light up as you press them, and the window's shortcuts. The composer and its Send tooltip follow the choice.
- Artifacts: a lead can answer with an `artifact` code block of HTML that the transcript renders inline as a visual (timelines, flows, pipelines, charts, stats, cards, tabs), built from `@cerium/artifacts` building blocks and design tokens in a sandboxed frame that runs no agent scripts and loads nothing from the network; agents read the blocks through the bus's `artifact_guide` tool.
- `@cerium/orchestrator`: a stopped or failed lead, including any after a restart, resumes its harness session when the user messages it again; approvals its old session left open are closed as denied, and the lead is told when the agents it spawned are gone.
- UI: a thread whose lead has stopped keeps its message box, and the next message picks the thread back up; only a lead that ended before its session started still offers a new thread.
- `@cerium/harness`: adapters list the models their harness offers; the Claude adapter asks the installed Claude Code.
- `@cerium/rpc`: each harness's models.
- Codex adapter: drives the user's installed `codex app-server` over JSON-RPC, with types generated from it: login and plan, the picker's models, threads with Cerium's bus injected and native subagents off, approvals for commands, file changes, MCP tools and permissions, file change tracking, per-turn usage, mid-session model and effort switching, interrupt and resume. Tested against a recorded session and verified live.
- Muse adapter: drives the user's installed `muse serve` through `@muse-code/sdk` with its schema pinned: login status, models, sessions with Cerium's bus injected and native subagents off, approvals answered with Muse's own choices, file change tracking, per-turn usage (and cost where Muse prices it), model and effort switching, interrupt and resume. Tested against a session recorded on Muse's offline provider.
- `@cerium/harness`: adapters can run their harness SDK's own browser sign-in, and `@cerium/rpc` starts it.
- UI: Harnesses settings sign in a harness whose SDK has its own browser sign-in: the button opens the harness's page in the browser, waits for you to finish there, then checks again. The SDK keeps the key it creates.
- Cursor adapter: runs Cursor's agent in-process through `@cursor/sdk`: models, sessions with Cerium's bus injected and native subagents off, file change tracking, per-turn usage, model and effort switching, interrupt and resume, and signs in from Harnesses settings with the SDK's own browser login. Cursor can't ask before using a tool, so modes that ask hold back the tools that would need it.
- `@cerium/backend`: registers the Codex, Muse and Cursor adapters beside Claude; until onboarding builds the catalog, a lead may spawn any model a logged-in harness offers.
- UI: tool calls from Codex, Muse and Cursor read like Claude's, naming the file read or edited, the command run or the pattern searched, and Harnesses settings say how each harness is signed in.
- CI on GitHub Actions for every push to main and every pull request: commit messages are checked against the rules in `CONTRIBUTING.md`, formatting, lint, types and tests run on Linux, then the tests run and the installer is built on Windows. Dependabot keeps the workflows' pinned actions current.
- `bun run build` builds every workspace package that has a build, and `scripts/check-commits.ts` checks a range of commit messages locally.
- Desktop: `bun run package` builds an unsigned Windows installer with electron-builder. The installed app starts its own backend in the background, keeps its data in the app's data folder, restarts the backend if it stops, and shuts it down cleanly on quit.
- `bun run dev` starts the backend, the UI's dev server and the desktop window together in one terminal, each line labelled with where it came from; closing the window or pressing Ctrl+C stops all three. `bun run dev --browser` leaves out the window.

Claude and Codex list their skills for a folder; Claude's come from a session that is never sent a prompt or saved.
- `@cerium/rpc` and the backend: searching a folder's files and folders (git's own listing, or a walk outside git), listing a harness's skills (kept for a minute), keeping pasted files that have no path of their own, and reading images for the UI.

- Backend: pasted files that were removed from the message box or never sent are deleted at startup once they are a day old; files a sent message carries are kept.
- `@cerium/store`: listing every thread's events of one kind.
- UI: `@` tags files and folders in the thread's folder and `$` the skills of the harness the message goes to, picked from a list above the message box (arrows, then Enter or Tab; Esc closes it). Each shows as a chip inside the text.

- UI: images an agent reads, or a tool returns, show as thumbnails on the folded tool line and full width inside the call, instead of their base64; clicking one enlarges it.
- `@cerium/store`, `@cerium/rpc` and the backend: saved projects. Every folder a work thread starts in, or that you choose, is kept with when it was last used; existing threads' folders are added when the database upgrades.
- `@cerium/store`, `@cerium/orchestrator`, `@cerium/rpc` and the backend: renaming a thread (trimmed, at most 80 characters) and archiving or restoring one. Archiving is refused while any of the thread's agents is working or waiting on you; neither counts as activity, so a thread doesn't turn unread or move.
- `@cerium/store`, `@cerium/orchestrator`, `@cerium/rpc` and the backend: deleting a thread for good, with its agents and their events. Its live sessions end first; like archiving, it's refused while any of the thread's agents is working or waiting on you.

Paste goes through the message box's own handling, so a copied screenshot becomes an attachment, as with Ctrl V.
- UI: right-clicking an inbox thread can also start a new thread in its project, show only that project's threads, rename the thread in place or archive it; right-clicking a chat renames or archives it. Settings → Archived lists archived threads and chats, most recently archived first, and restores them.
- UI: archived work threads wait in a folded "Archived" section at the foot of the Work sidebar, following the inbox's project scope and staying open or closed as you left it; right-clicking one restores, renames or deletes it. Every thread's right-click menu, and each row in Settings → Archived, can delete it for good after asking; deleting the open thread moves to a new one.
- UI: right-clicking a file or folder chip shows it in File Explorer, copies its path or its path relative to the thread's folder, or mentions it in your message.
- UI: right-clicking a message copies it (an agent's as Markdown), the text selected in it or a link in it; one of your own messages can go back into the message box with its tagged files and attachments.

Right-clicking an image in the conversation copies it, shows its file in File Explorer, or saves it where you choose (Pictures at first, then wherever you last saved one).
- UI: right-clicking an agent in the agents panel, or its card in the conversation, opens the same menu as its "More actions" button: show it in the agents panel, message the lead, interrupt its turn or stop it. Clicking a card opens that agent in the panel.
- `@cerium/protocol`: Cerium accounts: devices, the account's state as a machine knows it, the relay's API and messages, and device credentials (`cer1.<account>.<device>.<secret>`), which travel as a WebSocket subprotocol or a bearer token, never in a URL.
- `@cerium/relay`: Cerium's relay, a Cloudflare Worker with Durable Objects. A machine signs in on its page in the browser with Clerk and gets a device key of its own, of which the relay keeps only a hash. Each account is one object holding its devices and their live connections, which hibernate while idle; every change reaches every connected device. The first device is approved at once and later ones wait until an approved device allows them; approved devices can allow, deny, rename or remove any device.
- `@cerium/rpc`: watching this machine's Cerium account, signing in and out, and approving, renaming and removing the account's devices.
- Backend: signs the machine in through the user's browser and stays connected to the relay, pinging it, reconnecting with backoff when the line drops, and signing itself out when the relay says the machine was removed. The packaged app keeps the sign-in encrypted with Windows' data protection, through the shell.
- Desktop: while this computer is signed in, closing the window keeps Cerium running in the tray (Open Cerium, Quit Cerium), and agents at work keep the PC from sleeping. Launching Cerium again shows the window that's running. The installed app can start with Windows, straight to the tray.
- UI: Settings → Account: sign in with Google, GitHub, X or an email and password on Cerium's page in the browser; see the account's devices, which are online and when the others were last seen; allow or deny a device that wants to join, rename or remove one, or sign this computer out; and turn on starting with Windows. A notice above the thread says when a device wants to join, and opens the page.
- Development: `bun run dev` also starts the relay once its Clerk keys are set up, which `apps/relay/scripts/setup-clerk.sh` walks through.
- `@cerium/relay`: tunnels: an account's approved devices send each other RPC frames through their relay connections, which the relay passes on unread to a desktop or to the connection that asked, telling the sender when nobody can take a frame and everyone when a connection ends. Devices report the RPC version their backend speaks.
- Backend: other devices of the account drive this machine through the relay, with every RPC but the account's; and this machine's UI drives another one through `/remote`, which refuses machines that aren't online before connecting.
- UI: a machine picker in the titlebar, once the account has more than one computer: pick another online computer and the window shows its threads, projects, harnesses and settings, with the per-machine settings pages saying which computer they're about. Your account, the devices list and keeping this computer awake stay with this computer. Files and folders on the other computer aren't opened from here: attachments are sent as bytes, and folders are added in Cerium on that computer. When the computer can't be reached, a notice says so, with a way back to this one.
- `@cerium/relay`: the cloud copy of every computer's threads: their overviews and events (without streamed text or the provider's raw messages), stored in batches that resends and lost answers can't duplicate or reorder, and read by any approved device. Read state is kept for the account, the latest time any device saw each thread. Removing a computer takes its threads out of the cloud.
- Backend: while signed in, keeps the cloud copy of this computer's threads current, a second after new events and every 15 seconds for renames and archives, and resumes from where the copy ends after reconnecting. It serves the account's threads to its UI and reads other computers' threads from the copy.
- UI: one inbox for every computer of your account, each other computer's threads named with it (faint while it's offline). Opening one switches the window to its computer; one whose computer is offline opens read-only from the cloud copy, saying since when, and offers to open it there once the computer is back. Seeing a thread marks it read on all your devices.
- `@cerium/relay`: serves the web client at its root, beside the sign-in page, with a Content-Security-Policy that admits only the app's own scripts and its artifact frames' runtime. The sign-in page speaks to a phone or browser signing in ("Connect a device") and sends it back to the app once confirmed. `DEV_ORIGINS` lets the web UI's dev server sign devices in.
- UI: the web client, for your phone or any browser at Cerium's address: sign in there, wait for one of your computers to allow it, then work on your computers through Cerium's cloud, with one inbox for all of them, live threads, the composer, agents and settings. Below 768 px wide it's one pane at a time under a top bar with the way back, sized for touch, with long-press menus, past the notch and above the keyboard. It can be added to the Home Screen, follows the system's theme, and reads every thread from the cloud copy while none of your computers is online.
- UI: a computer's threads keep showing, from the cloud copy, while the window waits for it to answer or can't reach it.
- Development: `bun run dev:web` serves the web client with hot reload against the local relay, and `bun run --cwd apps/relay build` builds it into the relay's assets.
- Deployment: `apps/relay/scripts/deploy-relay.sh` walks through publishing the relay at cerium.nonlooped.xyz for the first time, with its Clerk and push keys as Cloudflare secrets, then installing a nightly that can sign in and connecting a phone.
- `@cerium/relay`: push notifications to the account's phones and browsers by Web Push, encrypted for each browser and signed with the relay's VAPID key (`node scripts/vapid.ts` makes a pair). None reach a browser while it shows Cerium, and none are about a thread a window shows on any device. A browser whose push service no longer knows it is forgotten.
- Backend: tells the account's browsers when one of this computer's threads waits for your approval, finishes or fails, with the request, the last message or the error. A thread settles for a few seconds first, so a request answered at once, a stopped turn or a helper agent handing its answer to the lead tells nobody.
- UI: Settings → Notifications in the web client turns notifications on for that phone, tablet or browser, and picks which: an agent needs you, a thread finishes, something fails. It works in any browser with web push; where a mobile browser notifies only web apps on the Home Screen, it shows how to add Cerium there first. Tapping a notification opens its thread. Every window tells your account which thread it shows, so you aren't notified about what you're looking at.
- Desktop: Cerium updates itself. Settings → Updates picks the channel to follow, stable or nightly, checks it, downloads the newer build and restarts into it. Cerium checks at launch and every six hours, and a notice over the conversation offers a newer build when there is one. Nothing downloads until you say so, and a nightly that switches to stable waits for stable to pass it rather than going back. Until Cerium's releases can be read publicly, updates say they're off.
- Auto access: each harness's own reviewer model approves or refuses an agent's edits and commands, instead of you or nobody. Claude runs in Claude Code's auto mode (asking you when its classifier can't decide, and as Ask first on models without it), Codex in "Approve for me", Muse in its `:auto-review` profile and Cursor with Auto-review. The composer and Agents settings offer it between Accept edits and Full access, and a lead in Auto can give its helpers Auto or less.
- `@cerium/bus`: agents can see and use a web UI like a user. `ui_open` opens a URL in your Edge or Chrome (headless, on a fresh profile) or attaches to an app's debugging port; `ui_act` runs a batch of clicks, typing, key presses, scrolls, drags, waits, navigation, scripts and file uploads, finding controls by their visible text or name; `ui_screenshot` and `ui_inspect` show the page as an image or as its controls and console errors; `ui_close` ends it. Each call that changes the page answers with a screenshot. Read-only agents can look but not act, and a page closes when its agent stops or sits unused for 20 minutes.
- `@cerium/bus`: `live_check` runs a short real turn on each harness and reports the tools it called, the approvals it asked for, the files it wrote and its reply, with a deadline per harness so a stuck session can't hang it. Results arrive as a message. In a Cerium checkout it runs the checkout's own `apps/backend/scripts/live-check.ts` (also runnable by hand) and needs Auto or Full access; elsewhere it uses the app's adapters. A check never gets more access than the agent asking.
- `@cerium/orchestrator`: agents that may act learn about the UI and live-check tools in their instructions.

### Changed

- `@cerium/harness` takes `AccessMode` from `@cerium/protocol` instead of defining its own.
- Desktop: nightlies are no longer a separate Cerium Nightly app. Stable and nightly builds are one app, Cerium, and the channel you follow in Settings → Updates decides which you get; releases carry the update files the app reads. A Cerium Nightly installed before this stays a separate app with its own threads (in `%APPDATA%\cerium-nightly`), and updates only reach Cerium: install Cerium, then uninstall Cerium Nightly when you no longer need its threads.
- The scripted fake harness adapter used in tests is shared from `@cerium/harness/testing`.
- `@cerium/store` applies its own bundled migrations unless given another folder.
- UI: agent markdown is sized for the conversation: compact headings, hanging list markers, inline code at the text's size, quiet blockquotes and links, and code blocks and tables as single cards with a copy button, without line numbers or download buttons.
- `@cerium/orchestrator`: sessions load the user's own MCP servers only while that setting is on (default on); it was always on.
- UI: the composer and Agents settings offer the models each installed harness actually lists, remembered by provider and model, instead of a fixed list. The last lists are kept so the pickers fill in before the harnesses answer, and "Check again" in Harnesses settings re-reads them.
- UI: Agents settings picks the lead model with one row per harness and a menu of its models, instead of a chip for every model.
- `@cerium/protocol`: a logged-out harness may offer a browser sign-in instead of a login command.
- `@cerium/protocol`: an adapter can declare that its harness has no approvals.
- UI: the tool calls and reasoning between two of the agent's messages fold into one line that counts what they did ("3 files read, 2 commands run"), opening on click. The stretch the agent is still working through stays open until it moves on.
- UI and artifacts: text is set in Red Hat Text and code in Red Hat Mono instead of Geist and Geist Mono, scaled to Geist's x-height so every size reads as before.
- UI: the Work sidebar is an inbox instead of per-project groups: every project's threads in one list, with those waiting on your approval or failed since you looked under "Needs you", then "Working", then "Unread" (finished since you last opened them), then the rest by day. Each row leads with the project's own icon (its favicon, icon or logo, found in the folder or its monorepo packages) or else its initials, with the thread's status as a dot on the badge's corner, and names the project, the git branch checked out there and the harnesses its agents use; a menu scopes the inbox to one folder (remembered) or marks everything read, and right-clicking a thread marks it read or unread. An unread thread you open keeps its place until you leave it. Today's threads need no heading when they top the list, and there is no "nothing needs you" line. Chats keep their list by recency.
- UI: a new work thread's project is chosen from a searchable list of saved projects, most recently used first, with each project's icon and where it sits, instead of opening File Explorer every time. Names that start with what you type come first; "Add folder…" browses for one and saves it; a project whose folder is gone is marked and can be removed from the list.
- UI: the transcript and the message box are 10% wider.
- UI: your messages keep their line breaks as typed, show their attachments above the text, and show tagged files and skills as chips.
- `@cerium/orchestrator`: the lead's instructions say when to answer with an artifact (a report on several pieces of work, a comparison, a sequence, numbers) and show a working one, instead of one closing sentence; every agent learns that `@path` names a file and `$name` a skill.
- Desktop: the installer's welcome and finish pages show the Cerium mark and name without the "Harness of harnesses" tagline.
- README: the banner is now the Cerium mark and name alone, in dark or light to follow GitHub's theme; the features and screenshots show the inbox, `@` and `$` tags, approval diffs and right-click menus; the light theme screenshot is gone.
- `@cerium/account`: what a device does with its Cerium account (the relay connection and sign-in, the account's threads and read state, tunnels to other computers, and the RPCs its own UI calls about them) moves out of the backend into a package of its own, so the web client can run it too. `@cerium/rpc` splits into what a machine serves (`MachineRpcs`) and what a device answers about itself (`DeviceRpcs`). A sign-in waiting for the browser now picks back up after a restart.
- UI: a calmer titlebar. The mark stands alone without the "Cerium" name and divider, the sidebar toggle sits over the sidebar's edge above search, and the machine picker moves to the right beside the agents button, opening its menu leftward.
- UI: Agents settings shows access as a table of modes against what each may do, with the chosen mode described beneath it, instead of a card per mode.
- UI: every new work thread starts in Auto access. Agents settings changes that default; picking another mode in the composer covers just the thread it starts, instead of becoming the next thread's mode too. An access remembered from before starts over at Auto.

### Fixed

- Desktop: Acrylic now shows through the window (the window is transparent), with edge resizing, Snap and Windows 11 rounded corners restored natively since Electron removes them from transparent windows.
- Claude adapter: trusted bus tools are approved inside the permission callback instead of through `allowedTools`, which bypassed the callback and triggered an SDK warning.
- `@cerium/rpc`: events reach the UI without the provider's original message, which isn't always strict JSON and ended the live event stream.
- UI: the message box no longer draws a second focus outline inside the composer's own focus border; components with their own focus style can opt out of the global ring.
- UI: picker labels in the composer stay on one line when space is tight.
- UI: logos of harnesses that can't run dim the same way whether the logo is in colour or not, in the sidebar and the model picker.
- UI: costs under a cent read "<$0.01" instead of "$0.00", and the inspector's latest message preview is plain text instead of raw markdown.
- UI: a thread whose lead has stopped or failed no longer offers a message box that can only fail; the composer says so and offers to start a new thread. Approval cards it left unanswered read as expired instead of offering buttons, and tool calls cut off mid-run read as interrupted instead of spinning forever.
- UI: the inspector only offers what an agent can do: "Message" moves to the composer for a live lead, "Interrupt turn" is only enabled mid-turn, and an agent that has stopped or failed has no actions. The "Open" button, which did nothing, is gone until agents get their own views.
- UI: stopping an agent from the inspector asks first, and says what stopping costs: a stopped lead ends its thread.
- UI: the inspector says "Just now" instead of "now ago", and an agent with no usage yet reads "None yet" instead of zero tokens and an unreported cost.
- UI: an empty sidebar explains where threads or chats will appear, and project groups use a plain folder icon, since a work folder needn't be a git repository.
- UI: the thread title in the titlebar is plain text instead of a button that opened nothing, so it drags the window like the rest of the titlebar.
- UI: the browser preview stands a light backdrop behind the light theme instead of the dark one.
- UI: notice bars carry a faint tint of their status colour, so they read as banners rather than stray lines over the transcript.
- `@cerium/orchestrator`: read-only agents no longer wait on approvals: Cerium approves their requests itself (web searches and fetches, reads outside the folder), for every provider, since each harness already keeps them from writing. These requests are never shown, not even briefly. Tools of the user's own MCP servers still ask.
- `@cerium/orchestrator`: stopping a subagent tells its lead, which otherwise waited for a result that would never come.
- Claude adapter: a permission request is ready for its answer before it is announced, so an immediate answer is no longer lost.
- UI: approval requests from subagents appear in a tray above the message box, one card per waiting agent with who is asking and how many requests are queued, and in the agent inspector when the subagent is selected. Before, they were counted as "Needs you" but could not be answered anywhere. A subagent's card in the transcript also says "Needs you" instead of "Working" while it waits.
- UI: a child agent's report or another agent's message longer than one line folds behind its first line, and opens as rendered markdown instead of one run of raw text.
- UI: typing `$` no longer flashes the files and folders an earlier `@` found while the skills load.
- Sending a message no longer leaves it unseen while the agent starts or finishes its turn: a new thread opens at once while its harness session starts behind it, and a message sent mid-turn shows as queued right away. A lead whose session never started gets a new one on the next message, and messages it never delivered go with it instead of being lost.
- Remote control: "Can't reach …" no longer shows for every dropped line. Coming back to the app, a network coming back or a computer waking checks its connection to Cerium's cloud at once and reconnects within seconds, where a dead connection could go unnoticed for up to 70 seconds; a tunnel to another computer counts as connected only once that computer answers; and the warning waits 8 seconds of being disconnected before it shows.
